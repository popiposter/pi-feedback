# PI Development Kit feedback

Public intake for reusable **1C Development Kit / Desktop integration** bugs,
missing capabilities and practices. This tracker is not a source mirror, binary
channel, support dump or implementation authority. Desktop binaries belong to
[pi-release](https://github.com/popiposter/pi-release/releases).

**Before posting:** remove credentials, tokens, source, logs, prompts, private
repository/task URLs, local paths, customer/business names and IDs, BookStack
content, test data and screenshots containing them. Use a small synthetic
reproducer. Do not attach private evidence. Private supporting evidence stays
on your workstation; state only whether a sanitized reproducer is available.

Report the public Desktop version, Development Kit bundle identity, relevant
EDT-MCP/tool version, generic capability/route, expected/actual behavior,
sanitized reproduction and whether project delivery is blocked. The installed
`1c-kit-feedback` skill can prepare a draft; posting always requires explicit
review and submission. No telemetry is collected.

**Security:** never file vulnerability details publicly. Use
[GitHub private vulnerability reporting](https://github.com/popiposter/pi-feedback/security/advisories/new).

Maintainers classify intake as project support, duplicate, kit candidate,
upstream tool, private security handling or insufficient evidence. A reusable
result can be marked `triaged`, `accepted`, `upstream`, `declined`, or
`fixed in <public version>`. PI implementation and private qualification occur
separately; reporters need no private repository access. Public replies never
include private issue numbers/links, source revisions or workstation evidence.

Fixes arrive through a Desktop release and **explicit project kit update/adoption**.
Application update does not rewrite receiving repositories. Verify the stock
kit on your project before retiring a local workaround; keep project policy
overlays and historical evidence bound to their original kit identity.

Templates require a redaction acknowledgement. GitHub issue forms cannot validate
arbitrary text against secrets: obvious unsafe fields must be flagged during
review and removed before submission. The optional helper refuses common secret,
URL and path patterns; that does not replace your review.
